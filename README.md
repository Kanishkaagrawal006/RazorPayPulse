# RazorPayPulse

### Intelligent Multi-Pass Payment Reconciliation Engine

RazorPayPulse is a Java/Spring Boot backend that automatically reconciles payment settlement records against bank statement entries using a **three-pass reconciliation pipeline**.

The system progressively moves from deterministic matching to rule-based matching and finally to **LLM-assisted reasoning with Google Gemini** for difficult cases.

The core design principle is:

> **Use deterministic logic wherever possible, and use AI only when additional reasoning is required.**

This makes the reconciliation process more explainable, auditable, and resistant to unreliable AI decisions.

---

## 🚀 Problem

Payment platforms generate large volumes of settlement records that must be reconciled with bank transactions.

In real-world reconciliation, records may differ because of:

* Settlement timing differences
* Processing fees
* Taxes
* Amount discrepancies
* Duplicate transactions
* Missing bank records
* Different payment references
* Bank narration variations

Manually investigating these cases is time-consuming and error-prone.

RazorPayPulse automates this process by progressively applying increasingly flexible matching strategies.

# 🔄 Reconciliation Pipeline

## Pass 1 — Exact Matching

The first pass handles high-confidence cases using deterministic matching logic.

The engine evaluates transaction attributes such as:

* Payment/settlement references
* UTR/reference numbers
* Exact amounts
* Transaction dates

No LLM is involved in this stage.

The goal is to resolve obvious matches quickly and deterministically.

---

## Pass 2 — Rule-Based Matching

Transactions that cannot be resolved by exact matching move to the second pass.

Pass 2 applies reconciliation rules involving:

* Amount tolerance
* Settlement date tolerance
* Payment references
* Bank narration
* Merchant/company references
* Previously consumed bank lines
* Narration similarity

This allows the engine to resolve records where the corresponding bank entry is valid but not an exact textual or numerical match.

---

## Pass 3 — LLM-Assisted Reasoning

The final pass is used for cases that remain unresolved after deterministic and rule-based matching.

Gemini receives a **restricted set of candidates** generated by the reconciliation engine.

The model evaluates information such as:

* Payment references
* Merchant/company references
* Amount agreement
* Date proximity
* Bank narration

A response follows a structured format:

```json
{
  "decision": "MATCH",
  "bank_line_id": 123,
  "confidence": 0.95,
  "reasoning": "The bank narration contains the matching payment reference and the amount and settlement date agree."
}
```

The application then validates the response before accepting it.

The model cannot select an arbitrary bank record. It can only select a bank line that was already supplied as a candidate by the Java reconciliation engine.

---

# 🧠 Why Multi-Pass Matching?

Using an LLM for every transaction would introduce unnecessary latency, cost, and probabilistic behavior.

Instead, RazorPayPulse follows a progressive strategy:

```text
                 High-confidence cases
                         │
                         ▼
                ┌─────────────────┐
                │     PASS 1      │
                │ Exact Matching  │
                └────────┬────────┘
                         │
                    Unmatched
                         │
                         ▼
                ┌─────────────────┐
                │     PASS 2      │
                │ Rule-Based      │
                │ Matching        │
                └────────┬────────┘
                         │
                    Unmatched
                         │
                         ▼
                ┌─────────────────┐
                │     PASS 3      │
                │ LLM-Assisted    │
                │ Reasoning       │
                └─────────────────┘
```

This provides a balance between:

* **Determinism**
* **Performance**
* **Explainability**
* **Flexibility**
* **AI-assisted reasoning**

# 🛡️ Validation and Safety

Financial reconciliation should not blindly trust model output.

RazorPayPulse treats LLM responses as **untrusted input** and validates them before persistence.

The application checks:

* JSON structure
* Decision type
* Bank line ID
* Candidate membership
* Confidence range
* Minimum confidence threshold

For example, if the model returns a `bank_line_id` that was not included in the candidate list, the application rejects the response.

Low-confidence responses are also rejected rather than automatically persisted as successful matches.

This keeps the financial matching logic under application control.

# 🔧 Configuration

Configure PostgreSQL in `application.properties`:

```properties
spring.datasource.url=jdbc:postgresql://localhost:5433/razorpaypulse_db
spring.datasource.username=<your-username>
spring.datasource.password=<your-password>
spring.datasource.driver-class-name=org.postgresql.Driver

spring.sql.init.mode=always
spring.sql.init.schema-locations=classpath:schema.sql

spring.jpa.hibernate.ddl-auto=none
spring.jpa.show-sql=false
spring.jpa.open-in-view=false
```

Configure Gemini using the environment/configuration mechanism expected by your Spring AI setup.

**Never commit API keys, database passwords, or other secrets to the repository.**

# 🎯 Key Design Decisions

## 1. Deterministic matching before AI

The system attempts deterministic matching before involving an LLM.

This reduces unnecessary AI usage and keeps high-confidence financial decisions reproducible.

## 2. Restricted candidate selection

The Java application determines the candidates available to the LLM.

Gemini does not have direct database access.

## 3. Confidence threshold

The application applies its own confidence threshold rather than blindly trusting every model response.

## 4. Validation before persistence

LLM output is parsed and validated before a match is persisted.

## 5. Explainability

The reasoning returned by the LLM can be stored alongside the reconciliation result, making difficult matches easier to investigate.

## 6. Exceptions are preserved

The system does not force every transaction into a match.

Ambiguous and unresolved cases remain visible for further investigation.

# 🔐 Future Security Architecture

The current implementation uses Google Gemini for LLM-assisted reasoning.

For a production-oriented confidential-computing architecture, a future version could move the sensitive reasoning workload to a locally hosted open-weight model running inside an **AWS Nitro Enclave**.

Conceptually:

```text
                    Spring Boot
                         │
                         ▼
                ┌─────────────────┐
                │ AWS Nitro       │
                │ Enclave         │
                │                 │
                │ Reconciliation  │
                │ Local LLM       │
                └────────┬────────┘
                         │
                       vsock
                         │
                         ▼
                    Parent EC2
                         │
                         ▼
                    PostgreSQL
```

A local model would avoid sending sensitive reconciliation records to an external LLM API.

Potential future components include:

* Open-weight local LLM
* AWS Nitro Enclaves
* KMS
* Nitro attestation
* Encrypted model/data handling
* vsock-based communication

**This is a future architecture and is not part of the current Gemini implementation.**

# 💡 Project Highlights

RazorPayPulse demonstrates how an AI component can be introduced into a financial backend without making the entire system dependent on probabilistic model output.

The architecture follows:

```text
          Deterministic Matching
                   +
             Rule Engine
                   +
             AI Reasoning
                   +
          Output Validation
                   │
                   ▼
       Intelligent Reconciliation
```

The result is a reconciliation workflow that combines **backend engineering, rule-based systems, database persistence, and AI-assisted reasoning**.
